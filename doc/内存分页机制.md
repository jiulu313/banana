

可以。分页是操作系统里最核心、也最容易一开始觉得抽象的部分。你现在已经做到 32 位保护模式、PMM、IDT，所以正好适合系统讲。

先抓住一句话：

> **分页，就是把 CPU 使用的虚拟地址，通过页表转换成真实的物理地址。**

不开分页时，你现在基本可以把地址理解成：

```text
CPU 使用地址 0x00100000
        ↓
直接访问物理内存 0x00100000
```

开启分页后，CPU 不再直接拿这个地址访问 RAM，而是：

```text
CPU 给出虚拟地址
        ↓
查 Page Directory
        ↓
查 Page Table
        ↓
得到物理地址
        ↓
访问 RAM
```

比如：

```text
虚拟地址 0x40001000
        ↓
页表映射
        ↓
物理地址 0x00201000
```

于是程序以为自己访问的是：

```text
0x40001000
```

实际上 RAM 访问的是：

```text
0x00201000
```

这就是虚拟内存最基础的机制。

---

## 为什么 OS 要这么麻烦？

如果没有分页，程序看到的就是物理内存。

假设机器有：

```text
128MB RAM
```

进程 A 使用：

```text
0x00100000 ~ 0x00200000
```

进程 B 也想使用相同地址怎么办？

没有虚拟内存的话，它们会冲突。

有分页以后：

```text
进程 A：

虚拟 0x00400000
      ↓
物理 0x01000000


进程 B：

虚拟 0x00400000
      ↓
物理 0x02000000
```

两个程序都可以觉得：

```text
我的代码就在 0x00400000
```

但实际映射到不同物理内存。

所以分页带来的第一大能力就是：

> **地址空间隔离。**

还有第二个能力：

> **内存保护。**

例如页表可以规定某一页：

```text
只读
不可写
用户态不可访问
不存在
```

于是用户程序就不能随便修改内核内存。

第三个能力：

> **虚拟地址不需要连续对应物理地址。**

比如虚拟内存看起来：

```text
0x40000000
0x40001000
0x40002000
```

连续三页。

实际物理内存可以是：

```text
0x01000000
0x03456000
0x00200000
```

完全不连续。

但程序完全感觉不到。

---

## 为什么叫“页”？

因为内存不是逐字节做映射，而是按固定大小块管理。

经典 32 位 x86 默认页大小是：

```text
4KB = 4096 bytes = 0x1000
```

所以物理内存可以想成：

```text
page 0   0x00000000 ~ 0x00000FFF
page 1   0x00001000 ~ 0x00001FFF
page 2   0x00002000 ~ 0x00002FFF
page 3   0x00003000 ~ 0x00003FFF
...
```

虚拟内存同样按 4KB 页划分。

分页做的事情本质就是：

```text
虚拟页号
   ↓
映射
   ↓
物理页号
```

页内的 offset 不变。

例如虚拟地址：

```text
0x00401234
```

假设：

```text
虚拟页 0x00401000
↓
物理页 0x002A0000
```

那么：

```text
offset = 0x234
```

最终物理地址就是：

```text
0x002A0000 + 0x234
=
0x002A0234
```

所以页表只需要决定：

> 这个虚拟页映射到哪个物理页。

页内偏移不用管。

# 32 位 x86 为什么是两级页表？

32 位地址一共有：

```text
32 bit
```

如果页大小 4KB：

```text
4KB = 2^12
```

所以最低：

```text
12 bit
```

用于页内 offset。

还剩：

```text
32 - 12 = 20 bit
```

用来表示虚拟页号。

如果直接搞一张超级大页表：

```text
2^20 = 1,048,576 个 entry
```

每个 entry 4 字节：

```text
1,048,576 × 4
=
4MB
```

也就是说，每个进程光页表就至少要 4MB，即使它只用了几页内存。

所以 x86 把它拆成两级。

虚拟地址拆成：

```text
31                    22 21                    12 11             0
+-----------------------+------------------------+----------------+
| Page Directory Index  | Page Table Index       | Offset         |
+-----------------------+------------------------+----------------+
        10 bit                  10 bit               12 bit
```

也就是：

```text
10 + 10 + 12 = 32
```

---

## 第一层：Page Directory

Page Directory 有：

```text
1024 项
```

因为：

```text
10 bit = 2^10 = 1024
```

每一项叫：

```text
PDE
Page Directory Entry
```

每个 PDE 指向一个 Page Table。

---

## 第二层：Page Table

每个 Page Table 也有：

```text
1024 项
```

每一项叫：

```text
PTE
Page Table Entry
```

每个 PTE 指向一个 4KB 物理页。

所以：

```text
一个 Page Table
=
1024 × 4KB
=
4MB
```

一个 Page Directory：

```text
1024 × 4MB
=
4GB
```

刚好覆盖整个 32 位地址空间：

```text
0x00000000
~
0xFFFFFFFF
```

# 举一个完整地址转换例子

假设 CPU 访问：

```text
虚拟地址 = 0x00403004
```

把它拆开：

```text
Directory index
Table index
Offset
```

计算方式：

```c
directory_index = virtual_address >> 22;
```

```c
table_index = (virtual_address >> 12) & 0x3FF;
```

```c
offset = virtual_address & 0xFFF;
```

对：

```text
0x00403004
```

结果大致是：

```text
directory index = 1
table index     = 3
offset          = 4
```

于是 CPU：

```text
CR3
 ↓
Page Directory

PDE[1]
 ↓
找到某个 Page Table

PTE[3]
 ↓
找到物理页，例如 0x00200000

再加 offset 4
 ↓

物理地址 = 0x00200004
```

整个过程：

```text
VA 0x00403004
        │
        ├─ directory = 1
        ├─ table     = 3
        └─ offset    = 4
        ↓
Page Directory[1]
        ↓
Page Table
        ↓
Page Table[3]
        ↓
physical page = 0x00200000
        ↓
+ 4
        ↓
PA 0x00200004
```

---

# CR3 是什么？

CPU 必须知道：

> Page Directory 在哪里？

答案就是：

```text
CR3
```

CR3 是控制寄存器。

里面主要保存：

```text
当前 Page Directory 的物理地址
```

例如：

```text
CR3 = 0x00300000
```

那 CPU 就知道：

```text
Page Directory
位于物理地址 0x00300000
```

所以你以后会看到：

```asm
mov eax, page_directory_address
mov cr3, eax
```

或者 C 内联汇编。

---

# CR0.PG 是什么？

光准备页表还不够。

必须告诉 CPU：

> 从现在开始启用分页。

CR0 的 bit 31：

```text
PG
Paging Enable
```

置 1：

```text
CR0.PG = 1
```

分页正式开启。

你之前进入保护模式时设置过：

```text
CR0.PE = 1
```

现在又会设置：

```text
CR0.PG = 1
```

所以可以把 CPU 状态理解成：

```text
最开始
Real Mode

↓ PE=1

Protected Mode

↓ PG=1

Protected Mode + Paging
```

分页不是另一个“模式”，而是在保护模式基础上增加地址转换。

---

# PDE / PTE 里面存的不只是地址

一个 32 位 PDE/PTE 是：

```text
32 bit
```

高位主要保存物理页地址，低位保存属性。

常见位：

```text
bit 0  P   Present
bit 1  RW  Read/Write
bit 2  US  User/Supervisor
```

例如：

```text
P = 1
```

表示：

> 这一页存在。

如果：

```text
P = 0
```

CPU 访问它就会触发：

```text
Page Fault
#PF
vector 14
```

`RW`：

```text
0 = read-only
1 = writable
```

`US`：

```text
0 = supervisor only
1 = user accessible
```

所以比如：

```text
entry = physical_address | 0x3
```

这里：

```text
0x3 = 00000011b
```

表示：

```text
Present = 1
Writable = 1
Supervisor = 0
```

也就是：

> 内核可读写，用户态不能访问。

# 什么叫 identity mapping？

我们第一次开启分页时，最安全的方法就是：

```text
虚拟地址 == 物理地址
```

例如：

```text
VA 0x00000000 -> PA 0x00000000
VA 0x00001000 -> PA 0x00001000
VA 0x00002000 -> PA 0x00002000
...
VA 0x003FF000 -> PA 0x003FF000
```

这就叫：

```text
Identity Mapping
恒等映射
```

为什么第一次要这么做？

因为当前 kernel 正在：

```text
0x10000
```

执行。

stack 在：

```text
0x90000
```

VGA 在：

```text
0xB8000
```

如果你一开启分页，却没有给这些地址建立映射，那么 CPU 下一条指令就可能找不到：

```text
EIP 对应的页面不存在
```

立刻 Page Fault。

甚至 Page Fault handler 自己也没映射，就可能：

```text
#PF
↓
处理 #PF 又失败
↓
Double Fault
↓
Triple Fault
↓
CPU reset
```

QEMU 看起来就像突然重启。

所以第一次我们先：

```text
前 4MB identity map
```

确保：

```text
kernel
stack
VGA
boot memory
E820 map
```

全部还能正常访问。

# 为什么一个 Page Table 正好能映射 4MB？

一个 Page Table：

```text
1024 entries
```

每个 entry：

```text
4KB page
```

所以：

```text
1024 × 4096
=
4,194,304 bytes
=
4MB
```

所以：

```text
Page Directory[0]
        ↓
Page Table 0
        ↓
负责：
0x00000000 ~ 0x003FFFFF
```

Page Directory[1]：

```text
0x00400000 ~ 0x007FFFFF
```

Page Directory[2]：

```text
0x00800000 ~ 0x00BFFFFF
```

每个 PDE 管 4MB。

# PMM 和 Paging 是什么关系？

这个特别重要。

你刚刚做的 PMM：

```text
Physical Memory Manager
```

负责：

> 哪些真实物理页是空闲的？

例如：

```c
void *page = pmm_alloc_page();
```

返回：

```text
物理地址 0x00200000
```

Paging 则负责：

> 把哪个虚拟地址映射到这个物理页？

比如：

```text
物理页：
0x00200000
```

我们可以映射：

```text
VA 0x40000000
        ↓
PA 0x00200000
```

所以：

```text
PMM
负责分配 physical page

Paging
负责 virtual → physical 映射
```

二者关系：

```text
             kmalloc / process
                    ↓
              Virtual Memory
                    ↓
                 Paging
                    ↓
               Physical Page
                    ↓
                   PMM
                    ↓
                  RAM
```

这才是后面真正的内存管理架构。

---

# 为什么虚拟内存特别适合进程？

假设以后 banana 有两个程序：

```text
Program A
Program B
```

它们都链接成：

```text
代码从 0x00400000 开始
```

没有分页会冲突。

有分页：

```text
Process A page directory:

VA 0x00400000
↓
PA 0x01000000


Process B page directory:

VA 0x00400000
↓
PA 0x02000000
```

CPU 切换进程时，只需要：

```text
切换 CR3
```

地址空间就跟着换了。

于是：

```text
同一个虚拟地址
在不同进程里
可以代表完全不同的物理内存
```

这就是进程隔离的基础之一。

# Page Fault 又是什么？

如果程序访问：

```text
VA 0x50000000
```

但对应 PTE：

```text
Present = 0
```

CPU 就触发：

```text
#PF
Page Fault
vector 14
```

并且把发生错误的虚拟地址放进：

```text
CR2
```

所以以后 Page Fault handler 会做：

```asm
mov eax, cr2
```

得到：

```text
到底访问哪个地址出错
```

Page Fault 不一定代表“程序崩了”。

现代 OS 会利用 Page Fault 实现很多高级机制：

```text
Demand Paging
Copy-on-Write
Lazy Allocation
Memory Mapped Files
Stack Growth
```

比如程序申请 100MB：

```text
malloc(100MB)
```

OS 不一定马上分配 100MB 物理 RAM。

它可以先只保留虚拟地址空间。

真正第一次访问某页：

```text
Page Fault
↓
OS 分配一个 physical page
↓
建立映射
↓
重新执行指令
```

程序甚至不知道发生过异常。

这就是虚拟内存非常强大的地方。

```text
CPU
 │
 │ Virtual Address
 ▼
+------------------------+
| Page Directory         |
+------------------------+
           │
           ▼
+------------------------+
| Page Table             |
+------------------------+
           │
           ▼
     Physical Page
           │
           ▼
          RAM
```

而负责找到最上层页目录的是：

```text
CR3
```

负责开关分页的是：

```text
CR0.PG
```

页面大小目前：

```text
4KB
```

虚拟地址拆分：

```text
10 bit Directory
10 bit Table
12 bit Offset
```

这几个概念彻底明白以后，再看我们上一课的 `paging_init()` 代码，就不会觉得它是在写一堆魔法数字了。
